Selecting Slurm-compatible CPU targets
======================================

The optional ``spack slurm-target`` command discovers CPU targets of compute
nodes in Slurm and selects a target compatible with **every** node in the
selected set. Unlike ``spack arch --target``, it does not use the login node's
CPU target.

The resolver uses Archspec's microarchitecture parent graph, keeping specific
microarchitectures where possible, rather than sorting CPU names by age. It
uses the greatest shared generic ISA level only when a unique, more specific
common ancestor does not exist.

CPU inventory
-------------

Slurm does not automatically provide an Archspec CPU target. Cluster
administrators can add **exactly one** ``archspec_<target>`` entry to each
node's ``AvailableFeatures`` (e.g. ``archspec_skylake_avx512``,
``archspec_zen3``). If ``ActiveFeatures`` also contains an Archspec
label, it must match the available label; otherwise discovery fails closed.
Use ``spack arch --known-targets`` to see accepted names.

.. code-block:: console

   $ spack slurm-target detect --partition cpu --verbose-nodes

If features are missing, ``--source auto`` explicitly starts bounded
``srun`` probe allocations for untagged nodes, or ``--source probe`` for all
nodes. The probe runs ``spack arch --target`` on each selected compute node.
By default more than 32 probes are refused. The nodes must be schedulable,
and Spack's executable must be accessible to compute nodes. Drained and
offline nodes are **not** silently excluded: publish features or supply an
audited inventory instead.

For offline testing, ``--source file --inventory nodes.json`` reads a JSON
object mapping node names to Archspec targets. This is **not** checked
against live Slurm membership and must be independently audited for
deployment. The ``--partition`` selector is rejected with file inventories;
create a separate file with the desired nodes instead.

Build with a compatible target
------------------------------

.. code-block:: console

   $ spack slurm-target spec --partition cpu --source auto -- zlib
   $ spack slurm-target install --partition cpu --source auto -- zlib

To save and reuse a strict Spack configuration scope:

.. code-block:: console

   $ spack slurm-target sync --partition cpu --source features --scope ~/.spack/slurm-cpu
   $ spack -C ~/.spack/slurm-cpu spec zlib
   $ spack -C ~/.spack/slurm-cpu install zlib

The generated scope contains ``packages.yaml`` with both a target preference
and ``require: target=<name>`` to constrain the solver, and
``concretizer.yaml`` allowing the compute target to differ from the host.
``slurm-target.json`` records the mapping and provenance. No global Spack
configuration is modified. Re-sync after changes in cluster membership;
existing concrete environments are **not** rewritten automatically. Config
scopes generated by earlier prototypes without JSON provenance may require
migration to a fresh scope before re-syncing.

Limitations
-----------

* All selected nodes must share a CPU architecture family and compatible
  OS, libc, MPI and compiler ABI. CPU ISA compatibility alone does not
  guarantee binary portability between OS environments or accelerators.
* ``host_compatible: false`` permits compute-only targets, but does **not**
  make running compute-only build-time executables on the login node safe.
* Slurm features are administrator-maintained metadata, not CPUID. The
  available/active consistency check cannot verify the actual CPU ISA. CPU model
  names are **not** Archspec targets.
* An ``all`` packages requirement can be inappropriate for frontend-only
  tools and externally built dependencies; use separate Spack environments
  or scopes when necessary.
* ``srun --immediate`` probing can fail for allocated/offline nodes; this
  command intentionally fails closed, rather than omitting nodes.
* Compiler support for specific targets can limit concretization; the target
  resolver is **not** a runtime benchmark.
